# AI Context: SEIAN Power Plane PSCAD Workflow

Last updated: 2026-09-04 06:45 Asia/Colombo

## Project Goal

Build a research-focused co-simulation layer for SEIAN AMRP where the networking/control-plane simulator behaves like an SDN controller and sends switching decisions to a PSCAD LV power-plane simulation.

The colleagues' cloned AMRP simulator is kept unchanged at the repository root. All new power-plane/PSCAD work lives in the sibling-level folder:

```text
research_power_plane/
```

## Quick Start

```powershell
# 1. Rebuild the PSCAD feeder from scratch (clears + regenerates Main canvas,
#    rewrites the component map). Needs PSCAD running; self-heals if PSCAD has
#    an unrelated workspace open.
py research_power_plane\scripts\build_lv_feeder.py

# 2. Run all five experiment scenarios and record measured results.
py research_power_plane\scripts\run_scenarios.py
#    -> research_power_plane\pscad_workspace\scenario_results.json

# 3. Tests (no PSCAD needed).
py -m pytest tests research_power_plane\tests -q

# 4. Dashboard.
py research_power_plane\run_dashboard.py
```

Do **not** run step 2 (or `cli.py --execute-pscad`, or the dashboard's PSCAD
execution) while another PSCAD automation session is attached -- see Known
Limitations.

## Current Architecture

```text
AMRP/SDN controller output (fault events)
  -> seian_power_pipeline.controller_adapter          (optional format bridge)
  -> controller command JSON
  -> seian_power_pipeline.control_plane.NetworkControlCommand
  -> seian_power_pipeline.power_plane.PowerPlaneState  (safety/reachability replay)
  -> final switch-state PSCAD manifest
  -> PSCAD const "Value" writes (breaker control signals)
  -> PSCAD build/run
  -> .psout channels -> JSON research artifact / dashboard charts
```

## Current PSCAD Reality

`SEIAN_LV_Switching` is a real, working LV EMT feeder matching
`examples/lv_power_plane_microgrid.json`. It builds with **zero errors and zero
warnings**, runs, and produces **20,001-sample** waveforms per channel.

Contents (all generated by `scripts/build_lv_feeder.py`):

- `master:source3` Thevenin source at G01 (0.4 kV LL, 50 Hz).
- Six named buses (G01, N02..N06), each at a pairwise-distinct X coordinate so
  auto-routed wires can never cross an unrelated bus.
- Seven line branches, one per logical switch ID:
  `multimeter` (P/Q/Irms) -> `breaker3` -> `resistor` + `inductor` -> bus.
- Per-line breaker control: `const` -> `datalabel(Name=<line_id>)`.
- `Yload` at N02..N06; `multimeter` (Vrms) at every bus.
- 20 `datalabel` + `pgb` recorder pairs (6 bus voltages, 7 line currents, 7 line powers).
- One `ground`, tied to the source neutral.

### How switching actually works (this took several wrong turns to find)

`breaker3.NAME` is **not** a label -- it is a *control signal reference*. The
breaker reads a real signal of that name every timestep: **0 = closed,
1 = open**. So the control chain is:

```text
const.Value  ->  datalabel(Name=<line_id>)  ->  breaker3(NAME=<line_id>)
```

The dashboard/CLI switches a line by writing that `const`'s `Value`, which is
exactly what `seian_pscad_component_map.generated.json` binds:

```json
{"line_id": "SW_N04_N06_TIE", "component_id": 123456,
 "closed_parameter": "Value", "closed_value": 0, "open_value": 1}
```

Two dead ends worth not repeating:

- **`breaker3.BOpen1/2/3` does nothing.** They are GUI *animation state* only.
  Setting them reads back correctly (`"OPEN"`) while the breaker keeps
  conducting -- the giveaway was tie lines carrying 18 A while nominally open.
- **`Sequencer_Breaker.OpenClos` does nothing on its own.** It needs real
  time-triggering logic (IState/OState chained to a timer/fault signal). It
  satisfied the build-time name reference, which masked the problem.

### How measurements actually get recorded

PSCAD records a channel only for a `pgb` ("Output Channel") fed by a real
signal. The chain is:

```text
multimeter signal-name field (Crms/CurI/P/Q/Vrms)
  -> datalabel(Name=<signal>)  ->  pgb(Name=<signal>)  ->  .psout channel
```

A component's `animate="true"` fields (`Pd`/`Qd`/`Vd`, `BOpen*`) *do* appear in
the `.psout` but only as ~3-sample GUI-animation snapshots, and they do **not**
track switching correctly -- an earlier version of this model used them and
reported stale power on freshly-opened lines. They are not used for results.

Recorded channels: `Vrms_<node>` (kV), `Irms_<line_id>` (kA),
`P_<line_id>` (MW), `Q_<line_id>` (MVAR).

> **Coupling to watch.** These signal names are assigned in
> `build_lv_feeder.py` but consumed in two other places:
> `pscad_mcp_client.RECORDED_CHANNEL_PREFIXES` (which channels the CLI/dashboard
> asks to read back) and `psout_channels.CHANNEL_GROUPS` (how they are grouped
> for plotting). Renaming a signal without updating both silently yields "no
> channels" and empty charts -- this already happened once when the meters were
> renamed from `V_*`/`PQ_*`. `tests/test_psout_channels.py::TestExtractChannelPaths`
> guards it.

## Verified Results

`scripts/run_scenarios.py` runs all five scenarios end-to-end in one PSCAD
session and writes `pscad_workspace/scenario_results.json`. Final steady-state
values (all 20,001 samples/channel):

| Scenario | Energized | De-energized | Key evidence |
|---|---|---|---|
| 01 no-fault baseline | all six | -- | 398.2 V at G01 falling to 382.0 V at N06; both ties 0.00 A |
| 02 single fault isolation | G01, N02 | N03, N04, N05, N06 | N03..N06 at **0.0 V**; every line except G01-N02 at 0.00 A; G01-N02 drops to 11.28 A (N02's own load) |
| 03 tie-switch restoration | G01, N02, N04, N05, N06 | N03 | N03 stays 0.0 V; N04/N05/N06 restored to 380-387 V **through the ties** (N02-N05 tie 32.54 A, N04-N06 tie 13.45 A) |
| 04 loop rejection | all six | -- | identical to baseline, ties still 0.00 A -- the loop-forming command was rejected and nothing was written |
| 05 degraded control plane | G01, N02, N04, N05, N06 | N03 | same final state as 03 (only command timing differs) |

Sanity checks that hold: node current balance at every bus; 55.0 A at
G01-N02 in baseline matches P/(sqrt(3)*V*pf) for the ~40 kW of connected load;
open breakers read ~5e-9 kA (1 MOhm leakage), i.e. genuinely open.

`run_scenarios.py` reads the `.psout` directly with `mhi.psout` rather than
through the MCP server, so it is not subject to the server's 30-channel
read cap and gets full-resolution traces.

## Known Limitations / Follow-ups

- **Snapshot-per-run, not a mid-run switching event.** Each scenario applies
  its *final* switch state, then runs. The 20k-sample traces therefore show the
  energization transient of that configuration, not a breaker opening partway
  through a single continuous run. For a paper figure showing an actual
  switching transient, drive the breaker control signal from a time-based
  source (e.g. a comparator on `TIME`, or `timed_breaker_logic`) instead of a
  `const`, and extend `time_duration` past the switching instant. The scenario
  command timestamps (up to 45 s in scenario 05) are currently logical
  ordering only -- they do not drive PSCAD time.
- **Never have two PSCAD sessions on this workspace at once.** `cli.py
  --execute-pscad` and the dashboard each launch their *own* `PSCAD.exe`. If
  another automation session (e.g. an MCP `mcp__pscad__*` session) is attached
  at the same time, two processes write the same `.pscx` and you get either
  canvas duplication (build reports many "Position is exactly on another
  instance" warnings, then dimension-mismatch errors) or channel values that
  silently come from the wrong process's run -- observed as a scenario
  reporting baseline numbers. `run_scenarios.py` exists to avoid this: it does
  everything in one process. Recovery from duplication is re-running
  `build_lv_feeder.py`.
- **PSCAD reopening an unrelated workspace** (the sibling `AIDataCenter` PhD
  project) is a recurring failure mode on this machine and was half of the
  original "I don't see anything meaningful in PSCAD" symptom.
  `build_lv_feeder.py` and `run_scenarios.py` both self-heal via
  `pscad.load(WORKSPACE_FILE)`.
- **Component IDs change on every `build_lv_feeder.py` run** (it clears and
  rebuilds the canvas). The component map is regenerated in the same pass, so
  just don't hand-carry IDs across a rebuild.
- **Electrical parameters are illustrative.** 0.4 kV / 50 Hz, `R_OHM_PER_KW`
  line-impedance scaling, and `LOAD_KW` per-node demand were chosen because the
  topology JSON carries only `capacity_kw`. See the constants at the top of
  `build_lv_feeder.py` and swap in real cable/load data when available.
- **`controller_adapter.py` is written against the colleagues' current
  `FaultEvent`/`EventRecord` shapes**, not a frozen spec. When the real
  controller output format lands, extend `_FIELD_ALIASES` and
  `commands_from_fault_events` rather than reworking the conversion logic.
- A handful of `.psout` channel *names* for the unused animate fields come back
  with stray non-printable bytes (a server-side parsing quirk). Harmless now
  that results come from `pgb` channels, but `_extract_channel_paths` filters
  them out defensively.

## Environment Notes

- **PSCAD MCP allowlist.** The `pscad` MCP server is registered globally in
  `~/.claude.json` (`mcpServers.pscad.env.POWERIO_MCP_ALLOWED_ROOTS`) and was
  originally scoped only to the sibling `PSCAD_Model_AIDataCenterLoad` project,
  which made `list_output_channels`/`read_output_channels` refuse this
  project's files. This repo's path has been appended (user-approved). The
  server reads that env var at startup, so **a change there needs the MCP
  server/session restarted** to take effect. The CLI/dashboard are unaffected
  either way -- `pscad_mcp_client.py` launches its own MCP server subprocess
  and sets `POWERIO_MCP_ALLOWED_ROOTS` per invocation to `Path.cwd()`.
- `mhi.pscad` (automation) and `mhi.psout` (results reader) are both installed
  and used directly by the scripts; the MCP server is only one of several ways
  in, not a requirement.

## Important Discovery (historical)

PSCAD's generated Windows batch initially used `SEIAN_LV_Switching.exe ...`,
which failed because the current directory is not searched for bare
executables. `pscad_mcp_client.py` patches generated run batches to
`.\SEIAN_LV_Switching.exe ...`.

## Safe Operating Notes

- Do not edit root simulator files unless explicitly requested.
- Use `research_power_plane/` for all new PSCAD/research work.
- Regenerate the case with `py research_power_plane\scripts\build_lv_feeder.py`
  (it deletes and rebuilds the whole `Main` canvas -- don't run it after manual
  GUI edits you want to keep).
- Run experiments with `py research_power_plane\scripts\run_scenarios.py`.
- If PSCAD opens an unrelated workspace, either script fixes it automatically.
